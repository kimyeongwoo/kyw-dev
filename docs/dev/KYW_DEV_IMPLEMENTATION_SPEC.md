# kyw-dev 개선 구현 명세 — Codex 개발자 전달용

작성일: 2026-09-05 (KST)  
역할: 사용자 = 제품 책임자 / ChatGPT = 기획·PM / Codex = 개발자  
상태: 승인된 제품 방향을 구체화한 구현 요청. 구현·테스트 완료 보고가 아니다.  
원격 확인 기준: `main` / `b3b968d24a4b0eae6fd688791b436d8bffd60e1a` / 소스 패키지 `0.2.3`.

## 1. 목표와 확정 결정

이 하네스는 다른 프로젝트의 기능을 개발할 때 사용자가 매번 작업 방식을 설명하거나 진행을 관리하지 않아도 되도록 돕는다. 모든 작업에 동일한 문서·질문·검토·테스트 횟수를 부과하는 도구가 아니다.

확정한 기본 흐름은 다음과 같다.

```text
작은 작업: 요청 → 관련 맥락 확인 → 구현 → 필요한 검증 → 결과 보고
기록이 유용한 작업: 요청 → 최소 Task → 구현·검증 → 기록 갱신·보고
외부 작업: 해당 작업과 대상에 대한 사용자 승인 범위에서만 실행
```

Task는 재개·인계·중요 결정·실제 의존성의 추적에 도움이 될 때 사용한다. 사용자가 기록 작성을 명시하면 작업이 작아도 작성한다. 파일 수·소요 시간·코드 줄 수로 기록을 강제하지 않는다. Task가 없어도 구현·검증 품질 기준은 같다. 작은 권한 수정처럼 영향이 큰 변경은 기록 유무와 관계없이 충분히 검증한다.

여섯 스킬은 선택 도구다. 인터뷰 → 초기화 → Task → 구현 → 감사 → 배포를 모든 요청의 필수 순서로 만들지 않는다. 기존 모델·추론 설정과 호스트의 세션 관리를 유지한다.

이 문서는 이전 PM 검토안과 구현 지시서의 실행 범위·모호한 사항을 정리한 이번 전달본이다. 이전 문서들을 추가 체크리스트처럼 중첩하지 않는다. 상위 지시와 안전·권한 조건을 준수하고, 기존 제품 문서와의 차이는 승인된 제품 변경으로 정합성을 맞춘다.

## 2. 이번 개발 실행의 범위

이 명세와 동봉 프롬프트를 전달받은 Codex는 관련 소스·테스트·제품 문서의 로컬 수정, 필요한 검증, 결과 보고까지 진행한다. 설계 설명만 제출하고 멈추거나 묶음마다 승인을 다시 요구하지 않는다. 내부 구현 방식과 작은 리팩터링은 위임한다.

이번 전달로 작업 저장소의 커밋·푸시·PR 생성/갱신·병합·게시·태그/Release 생성·원격 workflow dispatch/rerun은 승인하지 않는다. 실제 배포, 버전 상승, 보호 규칙·권한·시크릿 변경, 사용자 전역 스킬 설치/업데이트, 유료 모델/API 비교도 범위 밖이다. 이 문서의 deliver/release 예시는 개발할 제품의 동작이지, 실제 외부 실행 지시가 아니다.

자체 소유 임시 fixture 안의 Git 초기화·커밋·로컬 원격 시뮬레이션, 임시 설치·패키징은 검증에 필요하면 허용한다. 실제 원격과 사용자 설치 영역은 변경하지 않는다. HTTP/GitHub/npm 쓰기는 테스트 대역으로 확인한다.

현재 브랜치·HEAD·diff·미추적 파일과 적용되는 AGENTS를 먼저 확인한다. 참조 SHA는 관찰 기준일 뿐 시작점을 강제하지 않는다. 과거 SHA로 reset/checkout하거나 자동 pull/rebase/stash/clean하지 않는다. 이미 있는 미커밋 구현과 `docs/dev/` 등의 사용자 자료를 보존하고, 반영된 개선은 검증 후 중복 구현하지 않는다. 원격 조회 불가만으로 독립적인 로컬 구현을 막지 않는다.

이 명세 때문에 하위 Task나 별도 진행 장부를 여러 개 만들지 않는다. 인계가 필요하면 최소 기록을 사용하되 기존 작업을 처음부터 반복하지 않는다. 범위 안의 가역적인 선택은 판단해서 진행하고, 읽기로 해결할 수 없는 중대한 범위 충돌만 해당 부분을 보류한다. 독립적인 나머지 작업은 계속한다.

## 3. 개선 1 — 일반 프로젝트의 CI와 자체 게시 계약 분리

### 현재 관찰

`skills/kyw-deliver/references/delivery.md`는 일반 병합에도 공유 어댑터의 `check-ci`를 지시한다. `src/core/ci-evidence.mjs`는 `ci.yml`, `Required / credential-free CI`, `Validate selected CI results`를 요구한다. 다른 프로젝트의 정상적인 CI 형식과 충돌할 수 있다. [S1][S2]

### 구현할 행동

일반 PR 병합은 대상 저장소·PR 번호·현재 head/base, 적용되는 필수 검사·리뷰·보호 정책과 현재 병합 가능 상태를 사용한다. 타 프로젝트에 하네스 전용 워크플로·job·step 이름, `main`이라는 브랜치 이름, npm 또는 플러그인 구조를 요구하지 않는다. 검증 결과는 의도한 현재 PR에 결부돼야 한다.

기존 GitHub 도구/API의 authoritative 결과와 서버의 보호 기능을 활용하는 작은 통합을 우선한다. 전체 ruleset·권한 체계를 복제하는 정책 엔진을 만들지 않는다. 기존 `requireCanonicalCi`/게시 helper를 무작정 느슨하게 만들어 일반화하지 않는다. 전용 canonical 검사는 자체 게시 경계에 그대로 두고 일반 병합 경로를 구분한다. 기존 `check-ci`의 전용 의미와 필요한 호환성은 명시한다.

특히 아래 의미를 구분한다. GitHub 세부 동작은 공식 문서와 실제 사용 중인 CLI/API 계약을 확인한다. [E1][E2]

- 필수 검사 실패·pending·누락, 오래된 결과만 존재하거나 대상이 바뀐 경우에는 해당 병합을 진행하지 않는다. 비필수 검사의 실패를 하네스가 일률적으로 새로운 필수 gate로 승격하지 않는다. 단, 실제 완료 조건 위반을 발견했다면 별도로 보고하고 해결한다.
- GitHub가 허용하는 `skipped`/`neutral`과 필수 workflow 미실행으로 남은 pending을 혼동하지 않는다. skip을 실제 테스트 실행 성공이라고 보고하지 않는다. 현재 프로젝트가 추가로 요구하는 실행 증거는 존중한다.
- PR head에서 검증하는 프로젝트와 현재 head/base에 연결된 test-merge commit에서 검증하는 프로젝트를 모두 존중한다. 모든 프로젝트에 두 종류의 검증을 모두 새로 요구하지 않는다. 자체 게시의 exact main-push SHA 계약은 별개다.
- 검사 이름만 같은 다른 출처의 결과나 이전 결과를 현재 요구사항 충족으로 대체하지 않는다. required source가 지정돼 있으면 출처도 존중한다.
- 필수 검사/보호 정책이 없다고 확인한 상태와 조회 실패·권한 부족·불완전한 결과는 다르다. 빈 검사 목록이나 API 오류만으로 '규칙 없음'을 추정하지 않는다. 반대로 충분한 플랫폼 증거가 있는데 추가 관리자 API 접근을 새 필수 조건으로 만들지 않는다.
- 실제로 필수 CI가 없고 별도 프로젝트 요구도 없다면 하네스 때문에 CI를 새로 만들게 하지 않는다. 완료 조건·사용자 승인·대상 확인은 그대로 필요하다.

병합 직전 대상/head를 다시 확인하고 expected-head 조건을 이용한다. bypass/admin/force 경로로 우회하지 않는다. 기존 merge queue가 있으면 프로젝트의 정상 경로를 따르고, 대기열 등록·자동 병합 예약·실제 병합을 구분해 보고한다. 예기치 않은 예약이나 승인 범위 밖 후속 자동 동작을 만들지 않는다. 구현하지 못한 플랫폼 경계는 해당 외부 작업의 제한으로 보고하고 로컬 완료를 무효화하지 않는다. [E2]

### 자체 배포의 적용 범위

`$kyw-deliver --release <version> --sha <sha>`의 기존 npm 게시 경로는 kyw-dev 유지보수용임을 문서·라우팅에서 명확히 한다. 다른 프로젝트에는 자체 publisher를 묵시적으로 적용하지 않는다. 다른 프로젝트의 배포 요청은 그 프로젝트에 이미 있는 절차와 현재 승인 범위를 이용한다. 절차가 불명확하면 제한을 보고하고, npm/OIDC 설정을 새로 구축하지 않는다. 범용 배포 provider 프레임워크는 만들지 않는다. [S6]

자체 게시의 canonical CI, 최신 run/attempt, exact SHA, OIDC, 버전·산출물·서명/provenance, 게시 결과 대조와 모호한 결과의 중복 게시 방지는 유지한다. 기존 유지보수 명령과 정상적인 재개 경로의 호환성도 보존한다. 대상 불일치는 설명만이 아니라 실제 호출 경계에서도 처리하여 자체 publisher·태그·Release 쓰기를 하지 않는다. 파일을 대규모로 이동·삭제할 필요는 없다. 일반 경로에서 호출하거나 요구하지 않는 적용 경계 분리부터 수행한다.

## 4. 개선 2 — 정확한 Task 대상에만 영향을 주는 검사

### 현재 관찰

`task-artifact-queue.mjs`의 좁은 선택 범위는 IMPLEMENTATION/EXACT에 적용된다. 정확한 DELIVERY에는 더 넓은 inventory 오류가 유지된다. 따라서 무관한 ID 충돌 등이 해당 Task의 PR 준비까지 차단할 수 있는 코드 경로가 남아 있다. 이번 관찰은 정적 소스 확인이며 새로 실행한 재현 결과가 아니다. [S3]

### 구현할 행동

정확한 ID의 PR 준비/병합 대상 선택에서는 선택한 Task, 관련 의존성, 실제 포함 변경, 대상 저장소·PR에 필요한 오류만 차단한다. 무관한 inventory 오류는 경고로 반환한다. 이 개선은 Task 선택의 범위를 줄이는 것이며, 별도의 PR·권한·CI gate를 생략하는 것이 아니다.

선택 ID 자체의 중복, 관련 기록·경로의 손상, 의존 그래프 오류, 경로 탈출, 소유권 불명확, 관련 생성/복구 트랜잭션은 계속 차단한다. 기존 소유권 증거가 정확히 비중첩을 증명하는 트랜잭션은 좁은 선택을 허용하되, 겹치거나 범위를 알 수 없는 트랜잭션은 임의로 무시하지 않는다. 잠금을 나이로 지우거나 기록을 삭제해서 통과시키지 않는다.

새 ID 할당·batch 생성·자동 다음 작업 선택은 이번에 무작정 완화하지 않는다. 필요한 전역 충돌 검사를 유지한다. 기록 경로의 비중첩이 실제 구현 파일을 동시에 덮어써도 된다는 뜻은 아니다.

## 5. 개선 3 — Task 없이 시작해서 PR·감사까지 이어지는 경로

### 현재 관찰

`kyw-impl`의 명시적 경로는 기존 ID 중심이다. 현재 스킬·파서·어댑터의 실제 연결을 확인해 문구 변경만이 아니라 사용 가능한 목표 기반 경로를 만든다. [S4]

### 이번에 제공할 명시적 사용법

아래 표는 구현 후의 목표다. 이 문서 작성 시점에 새 문법이 이미 지원된다는 뜻이 아니다.

| 호출 | 목표 동작 |
|---|---|
| `$kyw-impl "목표"` | Task 없이 목표를 구현·검증·보고한다. |
| `$kyw-impl 0042` | 기존 Task에서 구현/재개한다. |
| `$kyw-task "목표"` | 명시적으로 요청한 기록을 작성한다. 작성만 요청했으면 구현하지 않는다. |
| `$kyw-deliver` | 현재 요청의 변경 범위로 관련 커밋·non-force push·PR 준비를 수행하는 제품 경로다. Task는 요구하지 않는다. |
| `$kyw-deliver --merge` | 현재 작업에 대응하는 명확한 PR을 대상으로 명시적인 병합 경로를 사용한다. |
| `$kyw-audit` / `$kyw-audit --fix` | 현재 작업의 명확한 변경 범위를 감사하거나, 명시적으로 허용된 범위의 수정을 한다. |

기존 ID 기반 deliver/audit/merge와 한국어 관리 alias의 호환성을 유지한다. 위 스킬 호출의 인터페이스만 최소 확장하고, 기존 공유 어댑터에 필요한 분기/결과를 연결한다. 새 모드 설정 파일, 일곱 번째 스킬, 별도 구현 엔진, 모든 자연어를 가로채는 라우터를 만들지 않는다. 여섯 스킬의 explicit-only 정책은 유지한다.

Task 없는 경로는 `docs/tasks` 부재·과거 기록 오류·Task transaction 자체를 선행 조건으로 삼지 않는다. 가짜 Task ID, 임시 TASK 파일, 배포 버전 예약을 만들지 않는다. 다만 실제 수정할 경로와 다른 작업자가 충돌하면 그 충돌은 처리해야 한다.

현재 요청·diff·브랜치·기존 PR을 읽고 대상과 포함할 변경을 정한다. Task가 없다는 이유로 질문하지 않지만, 읽고도 관련 변경과 사용자 변경을 구분할 수 없거나 외부 대상이 여러 개라면 추측해 쓰지 않는다. 해당 부분에 필요한 질문만 한다. 자동으로 전체 변경을 스테이징하거나 무관한 파일을 포함하지 않는다.

목표 기반 입력과 ID·옵션을 모호하게 섞지 않는다. 빈 목표, 잘못된 옵션, 깨진 ID 호출이 우연히 다른 작업이나 배포 경로로 떨어지지 않게 한다. 기존 ID override와 alias 해석도 회귀 확인한다. 문자열 파싱이 사용자 승인이나 보안 격리의 증거가 되는 것은 아니다.

Task 있는 경로와 없는 경로는 같은 구현 원칙을 공유한다. 관련 맥락만 읽고, 승인된 목표의 가장 단순한 올바른 구현을 선택하고, 영향에 맞게 검증하며, 실제 결과와 한계를 보고한다. Task 없는 경로의 절차를 별도로 복제하지 않는다.

진행 중 인계 필요성이 생기면 사용자가 기록 생성을 금지하지 않은 범위에서 최소 기록을 보충할 수 있다. 이미 정한 설계·승인·검증을 다시 시작하지 않는다. 상태가 필요한 경우에도 기존 contract 5를 사용하고 새 계약 버전을 만들지 않는다.

## 6. 개선 4 — 감사의 결함과 검증 한계 분리

### 현재 관찰

감사 참조 문서는 `PASS`/`BLOCKED`를 사용하며, 증거가 충분하지 않은 경우도 BLOCKED로 표현한다. 실제 결함과 선택적 검증의 한계를 분리해 전달할 여지가 있다. [S5]

### 구현할 행동

감사 보고에는 실제 차단 결함, 수행한 검증, 미실행/불확실한 검증, 그 한계가 이번 완료 조건에 미치는 영향을 구분한다. 다음 표현이면 충분하다. 새로운 점수 시스템이나 감사 상태 DB는 만들지 않는다.

```text
판단: 확인한 범위에서 차단 결함을 발견하지 못함 / 구체적인 차단 결함 발견
검증: 실제 수행한 검사와 결과
한계: 실행하지 못한 검사와 이유
완료 영향: 필수 증거 누락으로 완료 보류 / 선택적 검사 한계이며 기존 필수 증거는 충족
```

테스트를 실행하지 못했다는 사실을 테스트 실패나 성공으로 바꾸지 않는다. 필수 증거 누락은 해당 완료·병합·배포에 반영한다. 검증이 어려워졌다고 필수 검사를 선택 사항으로 바꾸지 않는다. 반대로 선택적 추가 검사의 불가는 모든 작업의 실패나 무조건적인 재감사를 뜻하지 않는다.

기존 결과 필드/소비자가 있다면 호환성을 고려해 한계를 덧붙인다. 근거 없는 PASS는 허용하지 않는다. 완료가 보류돼도 이미 확인한 구현·검증 결과를 버리거나 Task를 불필요하게 초기화하지 않는다.

원본의 tracked/untracked/generated/cache/Task와 외부 상태를 보존한다. 테스트는 실제 도구가 쓰기·네트워크·자격증명을 제한하는 환경에서만 실행한다. 단순 복사는 sandbox가 아니다. Docker 등 격리 수단이 없으면 안전한 검토를 계속하고 위험한 검증을 미실행으로 보고한다. 감사가 자동으로 Docker를 설치하거나 호스트에서 위험한 테스트를 대신 실행하지 않는다. 이 개선을 위해 새 sandbox 계층을 만들지 않는다.

`--fix` 또는 이미 명확한 수정 승인이 있으면 그 범위 안에서 수정하고 관련 검증을 한다. 매 구현 완료 후 독립 감사를 자동 필수 단계로 추가하지 않는다.

## 7. 개선 5 — 검증·문서·설치 경로의 일관성

현재 이미 있는 Focused/Stable/Release 구분과 검증 재사용 원칙을 유지한다. 문서나 스킬에 남은 표현이 '어떤 작업이든 마지막에는 전체 검사를 다시 하라'로 읽히지 않도록 통일한다. 이 저장소를 검증하는 npm 명령이나 지원 OS/Node 매트릭스를 소비자 프로젝트의 요구사항으로 복제하지 않는다. [S7]

반복 검증 여부는 명령·관련 코드·테스트·설정·의존성·필요한 환경과 도구 버전의 변화, 실패 또는 구체적인 미해결 위험으로 판단한다. 문서에 적힌 PASS만으로 재사용하지 않는다. 다른 OS나 현재 결합 상태처럼 조건이 다른 검증, 필수 원격 CI를 같은 입력의 중복으로 취급하지 않는다.

스킬 본문, 참조 문서, `agents/openai.yaml`, 실제 파서/어댑터, README의 사용 예가 같은 행동을 설명하게 한다. 기존 SPEC·ARCHITECTURE·AGENTS·템플릿 중 의미가 바뀐 소유자만 수정하고 이 명세 전체를 여러 문서에 복사하지 않는다. 이 전달용 명세·프롬프트는 일회성 PM 자료이며 제품 패키지나 모든 프로젝트의 상시 지시에 포함하지 않는다.

패키지 방식과 직접 설치 방식에서 같은 동작을 확인한다. core 파일/참조가 추가·변경되면 hidden runtime, 관리 inventory, allowlist와 실제 tarball에 필요한 파일이 들어가는지 확인한다. 개발 소스에서만 통과하고 설치 후 실패하는 구현은 완료가 아니다. 사용자 전역 설치를 건드리지 말고 임시 fixture로 검증한다. 패키지/플러그인 버전은 작업 시작 시 값을 유지한다.

## 8. 구현 순서와 설계 재량

개선 1·2의 적용 범위를 먼저 분리하고, 개선 3의 Task 없는 경로를 연결한 다음, 개선 4·5의 보고·문서·검증 일관성을 맞추는 순서를 권장한다. 실제 코드 의존성에 따라 내부 순서는 조정할 수 있다. 이 순서는 고정된 단계 gate나 여러 차례 승인 절차가 아니다.

이번 수정 때문에 큰 historical hydration·설치 transaction을 전면 재작성하지 않는다. 기존 함수·공유 경로를 재사용하고 필요한 경계만 분리한다. 새 의존성, 범용 정책 엔진, 증거 DB, 스케줄러, daemon, 자체 모델 실행기, 다중 배포 adapter, 과거 Task/Test 일괄 변환, 고정 문서량·테스트 횟수 규칙은 범위 밖이다.

테스트 개수·파일 수·코드 줄 수의 감소를 목표 수치로 두지 않는다. 불필요한 작업이 없어지고 필요한 보호가 남았는지로 판단한다. 구현자가 더 단순한 설계를 찾았다면 같은 수용 조건과 보호 경계를 만족하는 한 채택하고 이유를 짧게 보고한다.

## 9. 검증할 대표 수용 조건

아래는 요구되는 결과다. 행마다 별도 테스트 파일이나 체크리스트 문서를 만들라는 지시는 아니다. 기존 테스트에 통합하고, 결정적 코드·fixture 검증과 실제 모델 행동 확인을 구분한다. 테스트 대역을 production 실행이라고 보고하지 않는다.

| ID | 시나리오 | 기대 결과·보호 |
|---|---|---|
| AC-01 | Task 폴더 없는 작은 목표 기반 구현 요청 | 공유 경로가 정상 연결되고 Task/TEST·전역 이력 조회를 강제하지 않는다. 실제 모델 구현 효과는 별도 관찰이다. |
| AC-02 | 기존 ID 재개, 관리 alias, 명시적인 기록 작성만 요청 | 기존 호환성·작성 범위·사용자 파일을 보존한다. 인계 기록 추가가 작업 재시작을 유발하지 않는다. |
| AC-03 | Task 없는 PR 준비·감사·병합 대상 | 현재 범위를 사용할 수 있고 Task를 소급 생성하지 않는다. 외부 대상/혼합 변경이 모호하면 추측해 쓰지 않는다. |
| AC-04 | 잘못된 목표·옵션·ID·문서 속 호출 문자열 | 엉뚱한 작업으로 fall-through하거나 외부 승인으로 승격하지 않는다. |
| AC-05 | 타 프로젝트의 다른 workflow/job/step·base 이름, 올바른 현재 증거 | 하네스 전용 이름 때문에 거부하지 않는다. 일반 경로와 자체 canonical 검사의 호출 분리를 확인한다. |
| AC-06 | 실패·pending·누락·잘못된 SHA/출처·오래된 결과·불명확한 정책 | 해당 병합을 허용하지 않는다. 로컬 작업은 보존한다. |
| AC-07 | 정상 skip/neutral, 현재 test-merge 검사, 확인된 필수 CI 없음 | 플랫폼과 프로젝트 정책대로 처리한다. skip을 실행 성공으로 과장하거나 빈 응답을 규칙 없음으로 추정하지 않는다. |
| AC-08 | 정확한 delivery 대상과 무관한 ID 오류·비중첩 생성 transaction | 경고 후 선택 가능하다. 관련 중복·경로/그래프 오류·겹침·불명확한 소유권은 차단하며 전역 할당 검사는 유지한다. |
| AC-09 | 감사에서 선택적 실행 환경 부재 vs 필수 증거 누락/실제 결함 | 안전한 검토를 계속하며 차이를 보고한다. 원본/외부 상태 보존과 격리 원칙을 유지한다. |
| AC-10 | 변경 없는 성공 검사 vs 관련 입력 변경 | 전자는 이유 없이 반복하지 않고 후자는 필요한 검증을 한다. 문구/fixture만으로 모델 행동 개선을 입증했다고 하지 않는다. |
| AC-11 | 자체 게시의 실패·응답 유실·충돌·게시된 대상 재개·다른 저장소 대상 | 기존 canonical CI와 중복 게시 방지·완료 효과 재사용 보호가 유지된다. 다른 저장소에 자체 publisher 쓰기를 하지 않는다. 실제 게시하지 않는다. |
| AC-12 | 실제 공유 adapter와 package/direct-install 경로 | 문서·명령·runtime imports가 연결된다. 필요한 회귀와 패키지 검증을 통과하고 기존 사용자 자료는 보존된다. |

변경한 실행 경로는 테스트 전용 복제 구현이 아니라 실제 공유 entry point/adapter를 통과하는 회귀로 확인한다. GitHub 쓰기 경로를 건드린 경우에는 실제 merge 인자/대상·expected head·우회 옵션 부재·거부 시 write 0을 테스트 대역 경계에서 확인한다. 소프트 가이드만 바꾼 행동은 코드 단위 테스트로 모델 행동을 보장했다고 표현하지 않는다.

먼저 관련 회귀를 수행하고, 마지막 입력의 결합 상태에서 현재 변경 영향에 필요한 통합 검증을 수행한다. 기준 커밋의 `npm run release:ci`는 `check`와 실제 tarball 후보 검증을 포함한다. 이번처럼 공유 runtime·CI 연결·패키징에 영향을 주면 최종 통합 검증이 필요하며 이 합성 명령을 사용할 수 있다. 이미 수행한 구성 명령들을 관례적으로 또 실행하지 않는다. 현재 checkout의 명령 구성과 필요한 수준을 먼저 확인한다. 로컬 검증 완료를 원격 CI 완료로 보고하지 않는다. [S8]

이전 PM 자료의 재현 결과나 과거 PASS는 참고다. 이번 수정의 실행 결과로 재사용하지 않는다. 환경 문제로 필수 검증을 못 했다면 그 범위·이유·남은 조치를 보고하고 완료라고 단정하지 않는다. 한 검증이 막혔다고 다른 가능한 구현·검증을 모두 중단하지 않는다.

## 10. 실제 사용 효과는 별도 관찰

이번 구현에서 시간·토큰 절감률이나 실제 모델의 과검토 감소를 증명했다고 주장하지 않는다. 유료 실행·새 평가 플랫폼은 만들지 않는다. 현재 승인된 세션에서 실제 확인한 행동만 보고하고, 나머지는 후속 실제 사용에서 확인할 항목으로 남긴다.

후속 평가는 작은 수정, 중간 규모 기능, 작업 재개, CI 구조가 다른 프로젝트를 대표로 삼을 수 있다. 동일 모델·추론 설정·초기 소스·도구 조건에서 완료 품질, 불필요한 재질문, 같은 입력의 검사 반복, 불필요한 파일 생성과 관찰 가능한 시간/사용량을 비교한다. 한 번의 성공을 일반적인 성능 향상으로 확대하지 않는다. 검증·안전성을 포기해서 얻은 속도 단축은 개선이 아니다.

## 12. 참고 소스와 작성 범위

2026-09-05 작성 과정에서 GitHub 연결을 통해 main SHA, 일반 병합 참조, canonical CI 검증, queue의 dispatch 구간, impl 스킬, audit 참조, package.json을 다시 읽었다. 아래 S6·S7의 내용은 같은 불변 SHA에 대한 앞선 검토를 이어받았다. 저장소 전체 테스트나 실제 모델·원격 쓰기 재현을 이번 문서 작성 중 새로 실행하지 않았다. 소스 관찰과 개선 요구를 혼동하지 않는다.

소스 경로는 탐색 출발점이며 수정 파일을 고정한 허용 목록이 아니다. 현재 checkout에서 호출자·테스트·설치 inventory를 따라 필요한 범위만 추가로 확인한다.
