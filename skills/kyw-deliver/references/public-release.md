The exact plain invocation carries one compound, attempt-specific authority for `npm publication → exact-SHA GitHub tag → GitHub Release`, in that order, after the unchanged `STANDARD` graph is final. It does not authorize a version change, public plugin-directory submission, dist-tag repair, asset upload, metadata edit, retry, rerun, fallback, force, deletion, bypass, account change, or another Task or repository.

## Classify all public state together

Use fresh cache-bypassed reads and complete bounded pagination to read all four surfaces before the first public mutation and again immediately before each applicable mutation:

1. public npm package/version, tarball, dist-tags, signatures, provenance, and prior-version history;
2. every bounded matching or potentially matching publication workflow run and attempt;
3. the exact Git ref namespace and direct or peeled `refs/tags/v<version>` target;
4. Release-by-tag plus any bounded duplicate or collision evidence in the exact repository.

Classify each surface and the aggregate plan as exactly one of:

- `ABSENT` — complete authoritative reads prove the object does not exist, with no matching active, completed, failed, ambiguous, or possibly accepted attempt. npm additionally requires an unchanged complete package index whose exact name/registry/version set and `latest` equal the frozen prior versions/`priorLatest`; a target-version 404 alone is unknown;
- `EXACT_ALREADY_COMPLETE` — fresh canonical data proves every required identity and immutable field equals the frozen tuple;
- `PENDING_PROOF` — one exact matching workflow is queued/in progress, or a single create request may have been accepted but canonical state is not yet conclusive; only observation is safe;
- `CONFLICT` — authoritative state exists but differs, is duplicated, is out of order, records a failed/cancelled/timed-out or superseding attempt, collides in namespace, or otherwise proves that creation/acceptance is unsafe;
- `UNKNOWN` — permissions, availability, cache bypass, pagination, parsing, peeling, provenance, identity, or eventual-consistency evidence is missing, partial, malformed, contradictory, or unreadable.

Only `ABSENT` admits that surface's one create action. `EXACT_ALREADY_COMPLETE` is read-only satisfied. `PENDING_PROOF` is observation-only. `CONFLICT` and `UNKNOWN` block. Do not collapse pending, conflict, or unknown into absence.

Evaluate ordering across surfaces, not each object in isolation. A tag or Release present before exact npm proof, a Release present without an exact tag, a duplicate Release, or another future-stage object while a prerequisite is absent/pending is `CONFLICT`. Do this whole-state preflight before an avoidable partial release, even when the next nominal stage appears absent.

## Perform the ordered public release

The fixed stages are `STANDARD_FINAL`, `NPM`, `TAG`, `RELEASE`, and `FINAL_PROOF`. Start at the first absent safe stage only after all earlier stages are exact and no later stage is out of order. After any request, perform bounded read-only reconciliation and require canonical exact state before advancing.

### 1. `STANDARD_FINAL`

Retain the production evaluator's exact final result, target merge SHA/tree, workflow identities, and post-main evidence. Recheck terminal-pair bytes and public tuple inputs. This stage performs no new mutation beyond the separately defined, already completed or resumed `STANDARD` lifecycle.

### 2. `NPM`

If npm is exact, skip dispatch and proceed only after the matching workflow run/attempt is also exact. If one exact matching run is queued or active, observe that run only. If a matching or potentially matching later run failed, was cancelled, timed out, is ambiguous, or supersedes an earlier success, block without falling back to the earlier attempt.

Only when the npm version and every relevant target run are authoritatively absent may the route dispatch `.github/workflows/publish.yml` once on the exact base ref. Its ten strings bind the frozen merge SHA, version, tarball byte count/SHA-256/shasum/integrity, packed-entry-set digest, prior-version-set digest, prior `latest` (literal `null` only when absent), and sole current registry signing-key ID. Revalidate workflow ID/name/path/active state, repository, ref, target SHA/tree, inputs, environment, and public registry immediately before dispatch. Do not trigger another workflow, rerun a workflow, use a local/token publish, or retry a rejected or lost dispatch.

The workflow is the sole npm mutator. Its one GitHub-hosted OIDC job checks out the real target Git directory, regenerates the bounded exact pack, and immediately rechecks frozen prior registry/latest/signing-key state, its sole first target run, absent target tag/Release, and clean checkout. Only then may it execute `npm publish . --access public --ignore-scripts --registry=https://registry.npmjs.org/` exactly once. It must not use a long-lived npm token, login/adduser/whoami/trust/account inspection, OTP/security-key interaction, lifecycle scripts, prebuilt-tarball publication, second dispatch, retry, fallback credential, independent dist-tag operation, tag creation, or Release creation.

Dispatch acceptance and successful workflow prose are not publication proof. Observe the exact run and authoritative attempt without rerun, then perform fresh cache-bypassed registry reads. Exact npm satisfaction requires all of the following to match the tuple:

- exact package, version, registry, public access, and `latest` state, with preserved expected prior versions;
- `gitHead` equal to the target merge SHA;
- fetched tarball raw bytes equal to expected bytes and its shasum/integrity/digests exact;
- a nonempty registry signature array whose every entry uses the frozen signing-key identity and cryptographically verifies the exact package/version/integrity message; one or multiple valid entries under that key are accepted and cardinality alone is not a conflict, while any mixed, malformed, or invalid entry fails the aggregate proof;
- SLSA provenance whose subject digest, repository, `.github/workflows/publish.yml`, `refs/heads/<base>`, run/attempt, and source commit bind the same target.

Missing or different immutable registry data is `CONFLICT`; evidence that cannot yet be read or verified is `PENDING_PROOF` only when bounded facts prove an exact in-flight/recent action, otherwise `UNKNOWN`. Never republish, unpublish, deprecate, retag, repair metadata, or dispatch again.

### 3. `TAG`

Accept an existing tag only when the exact `refs/tags/v<version>` namespace resolves directly, or by one unambiguous annotated peel, to the target merge SHA and no collision exists. Although an exact annotated tag may be read as an exact peeled target, creation by this route is always one lightweight ref directly at the target SHA.

A wrong target, ambiguous peel, namespace collision, duplicate, unreadable ref, lost response, or concurrent appearance blocks after bounded read-only reconciliation. ### 4. `RELEASE`

Enter only after npm and tag are `EXACT_ALREADY_COMPLETE`. Re-read all surfaces, including tag target, immediately before action.

Accept an existing Release only when fresh Release-by-tag and bounded duplicate reads prove the exact repository, tag, tag target, title `v<version>`, `draft=false`, `prerelease=false`, and empty assets. A draft, prerelease, wrong repository/tag/target/title, unexpected asset, duplicate, missing required field, or unverifiable object blocks without edit or replacement.

Do not upload assets, generate or infer notes, create an alternate Release, edit metadata, publish a draft, delete, or retry. Command exit, API acceptance, local checkout, cached data, workflow logs, CI success, or a prior report cannot substitute for this final proof. If any fact becomes pending, conflicting, unknown, or different, return `BLOCKED`; do not repeat an earlier mutation or continue to a later stage.

## Resume, ambiguity, and one-attempt limits

Every invocation reconstructs canonical state instead of trusting conversation history:

- all exact → read-only `FINAL_PROOF` and `COMPLETE`;
- exact `STANDARD`, absent npm/run/tag/Release → one npm workflow dispatch, then observation;
- one exact active publication run → observe it only;
- exact npm/run, absent tag and Release → one tag create;
- exact npm/run/tag, absent Release → one Release create;
- any out-of-order, failed, conflicting, malformed, partial, or unknown state → no write and `BLOCKED`.

Each externally visible mutator has a limit of one request or workflow-contained execution for the authorized attempt: inherited `STANDARD` actions retain their existing limits; workflow dispatch is at most once; workflow-contained `npm publish` is at most once; tag creation is at most once; Release creation is at most once. Failure, cancellation, timeout, lost response, runner error, API error, race, or eventual-consistency ambiguity consumes the applicable request boundary and permits only bounded canonical reads. It never grants retry, rerun, fallback, alternate credentials, a replacement object, or a later-stage write.

One attempt is one execution of the sole adapter under one exact plain invocation. These request limits are invocation-local: a later exact plain invocation is a newly authorized attempt, and separate or concurrent authorized invocations do not claim a distributed lock or globally exactly-once requests. Every such attempt still reclassifies canonical state first, skips exact state, observes pending state, blocks conflict or unknown state, and may issue its one request only for complete fresh `ABSENT` proof.

`npm-success/tag-failure` resumes by proving npm and inspecting tag; it never republishes or dispatches again. `npm-plus-tag-success/Release-failure` resumes by proving npm and tag and inspecting the Release; it never republishes or recreates the tag. A prior failed publication attempt remains authoritative even if an older attempt succeeded.
